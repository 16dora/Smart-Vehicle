# ESP32-CAM AP＋STA 摄像头与车辆控制（03）

独立 ESP-IDF v5.5.5 / CMake 工程，C++20。面向 AI-Thinker ESP32-CAM、OV2640、4MB PSRAM，按项目接线资料选择板型。

## 功能与默认值

- 复制自 02CameraWebServer，保留相机、OLED、车轮、机械臂和最新网页控制；本项目同时开启 AP 热点与 STA 路由器连接。
- 网页及相机端口 80、视频端口 81、运动端口 82；三者使用独立 HTTP 任务，运动接收优先级高于网页与视频服务。
- 默认 VGA（640 × 480）、JPEG 压缩值 12、发送上限 10 FPS。
- 分辨率：160 × 120、320 × 240、640 × 480、800 × 600、1024 × 768、1600 × 1200。
- JPEG 压缩值 10–63，越小画质越高。最大帧率 1–30 FPS，表示视频发送上限，不保证达到此帧率。
- 亮度、对比度、饱和度各 -2–2；支持水平镜像、垂直翻转和单张 JPEG。
- 显示当前积分时间估算值；支持自动曝光开关，关闭后使用毫秒数值框或滑块调节手动曝光。
- 网页显示最近统计窗口的实际发送帧率，并支持启动、停止预览。
- 页面显示 CPU 频率、双核忙碌率估算、内部/PSRAM 可用堆、Wi-Fi 信号及视频发送速率、平均取帧等待和发送耗时。
- 按根目录最新 `index.html` 接线方案，通过 PCA9685＋两块 TB6612FNG 控制四个电机；网页支持前后、左右平移、斜移、原地转向及占空比调速。
- 松手、失焦、切后台或网络断开时停车；独立任务每 50 ms 检查指令，500 ms 无有效续租即撤销输出。
- 设置只在本次运行有效，重启后恢复默认。当前仅面向一个视频查看者。

## 曝光显示与调节

### 可选百问网 OLED

支持 SSD1306 128×64 SPI OLED，默认启用 `CAMERA_OLED_ENABLED`。仅使用现有
`CameraWeb` 和主任务，不增加显示任务；每两秒显示 CPU0 / CPU1 忙碌率估算、
相机积分时间估算（ms）以及 AEC 开关。无需网页访问也会尝试采样曝光；相机忙时
不等待取帧，使用已有快照，超过十秒或读数无效显示 `--`；CPU 首轮建立基线时也显示 `--`。

| OLED 丝印 | 接线 |
|---|---|
| SCLK | U0R / GPIO3 |
| MOSI | U0T / GPIO1 |
| GPIO（D/C） | GPIO15 |
| CS、GND | 两针均接公共 GND |
| MISO | 不接，模块内部未连接 |
| 3V3 | ESP32-CAM 3V3 / 3.3V 母线 |
| 5V | XL4015 #2 的稳压 5V 母线 |

这块模块的 3V3 和 5V 分别接逻辑电源和屏幕 VCC，**两路都需要供电**；初始化关闭
内部升压泵，使用板载 RC 复位。SPI2 专用于 OLED，1MHz、模式 0、无 MISO、无 DMA，
CS 接地持续选中，不与其他设备共用时钟和数据线。内部帧缓冲为 1024 字节。

默认配置改为 `CONFIG_ESP_CONSOLE_NONE=y`，ESP-IDF 将控制台接到空设备，保留日志调用
但不输出 UART0，防止串口日志干扰 SPI；Bootloader 日志也关闭。ROM 启动输出仍可能存在，
应用会重新初始化并清屏。**烧录前断开 OLED 的 U0T / U0R 两根信号线，烧录后移除烧写板再接回**。
启用 OLED 时不使用 UART Monitor；需要串口诊断时，关闭 `CAMERA_OLED_ENABLED` 后选择 UART
控制台并重新构建。旧有生成配置不会仅因修改 defaults 自动迁移，本次同步更新了本地
独立的 `sdkconfig`；后续新建配置由 defaults 生效。

OLED 为可选外设，未接屏幕不会阻止摄像头和电机启动。SPI 只写没有 ACK，初始化返回成功
只代表控制器已配置及数据已发送，不能判断屏幕实际在线。接线图增加 OLED 开关以及独立
供电、SPI 两个视图；不接 OLED 时可隐藏该模块。

资料：[百问网说明](https://ldd.100ask.net/zh/11_SPI/08_1.html)、
[模块原理图](https://ldd.100ask.net/_images/49_oled_sch.png)。

“当前积分时间（估算）”读取 OV2640 硬件曝光寄存器，不使用驱动中可能过期的曝光缓存。
自动曝光默认开启；关闭时冻结当时的曝光及额外行，之后可在“手动积分时间（ms）”中调节。
滑块拖动仅更新本地显示，松开后提交一次；数值输入确认后提交。开启自动曝光后手动输入禁用。
自动增益仍按原配置开启，因此固定积分时间后画面亮度仍可能变化。

曝光以行周期量化，设备接收整数微秒并换算到最近的有效行数，界面回显实际寄存器对应的估算时间。
通常手动范围为当前模式的一帧以内，并受驱动快门上限 1200 行限制；若从更长的自动曝光切换，保留该曝光作为本次手动范围上限。
长曝光通过“快门行数＋额外曝光行数”表达，调短时会相应清除额外行，避免只能调长不能调短。
分辨率切换后重新读取时序，手动模式尽量保持原积分时间，超出新范围时取最近的有效值。
这些设置只在本次运行生效，重启恢复自动曝光。

换算依据为 [OV2640 数据手册](https://files.waveshare.com/wiki/common/OV2640DS_en.pdf) 的模式行宽、水平补偿与曝光寄存器定义，以及 [OpenMV OV2640 驱动](https://github.com/openmv/openmv/blob/master/drivers/sensors/ov2640.c) 的时钟模型。
JPEG 使用 YUV422 采集链路：`行周期 us = (模式行宽＋水平补偿) × 2 × 1e6 / 内部时钟 Hz`，其中 `内部时钟 Hz = XCLK × 3 × 倍频系数 / (CLKRC 分频值＋2)`；积分时间为有效快门行数与额外曝光行数之和乘以行周期。
该值为寄存器时序模型的估算，不是每帧光学实测；DVP 输出分频、网络发送上限和 JPEG 发送耗时不作为积分时钟。
曝光最多每两秒采样一次，复用现有状态轮询和视频统计发布，不增加任务或 HTTP 轮询。
视频占用相机锁时状态接口立即返回最近快照，不等待取帧；寄存器读数无效或采样时发生跨位变化时显示 `--`，下一轮重试。

## 设备运行状态

常规固件复用主任务每两秒采样一次，复用 `/status` 与网页原有轮询，不新增 HTTP 连接或统计任务。
首次采样建立 CPU 和视频计数基线，下一轮开始显示窗口值；临时性能构建沿用原有五秒主任务节拍。
统计独立于相机锁和视频发送，视频阻塞时仍可以更新 CPU、内存与无线状态。

- CPU 频率：读取运行时频率，单位 MHz，不用配置值冒充实际值。
- CPU0/CPU1 忙碌率：以每核空闲任务累计运行时间的窗口差值估算 `100% - 空闲比例`，每核范围 0–100%，不将双核相加显示为单核百分比。任务切换的计数结算和中断归属会带来误差，因此不是逐周期硬件测量。
- 网页运行统计独立启用 FreeRTOS 运行时间计数，不启用临时 `/perf` 接口。使用 ESP TIMER 微秒时钟；通过无符号差值处理 32 位计数回绕。首轮、异常计数、采样间隔超过一次回绕或不支持的统计配置会标记 CPU 读数不可用，不显示伪造负载。
- 内存：显示具备 8 位访问能力的内部可用堆和 PSRAM 可用堆，单位 KiB（1024 字节），不等于芯片全部 RAM 容量。
- 信号：STA 显示 ESP32 接收路由器的 RSSI；AP 显示所有已关联客户端中最弱的 RSSI，并显示接入数量。无客户端或 SDK 查询失败时显示 `--`；AP 信号不代表某个特定浏览器的下行质量。
- 视频速率：统计窗口内完整提交 HTTP 的 JPEG 字节数除以窗口墙钟时间，显示 KB/s（1000 字节/秒）与 Mbps（1000000 bit/s）。不含 MIME/HTTP/TCP 开销、重传、抓拍、网页或运动流量，不能当作整个 Wi-Fi 接口的总吞吐量。
- 帧在 HTTP 提交成功后才累计；传输失败前已部分提交的数据不计入。提交成功可能仍处于 TCP 缓冲中，不能据此断言浏览器已接收、解码或显示。
- 耗时：仅对窗口内完成提交的帧计算平均取帧等待和平均 HTTP 发送耗时。缓冲中已有图像时取帧等待可能接近零，它不代表积分时间；跨窗口的长耗时归入该帧完成时的窗口。
- 没有完成帧时，下一统计窗口视频速率为零，平均耗时显示 `--`。停止或重新预览不清空累计计数，窗口差值不会出现负值或回连突增。

页面显示统计窗口、完成帧数和采样年龄。状态请求失败或采样超过十秒时清除运行数值，显示 `--`，避免将旧数据误当作当前状态。
统计 SDK 查询与汇总日志使用低频输出，逐帧路径只更新四个累计数值，不额外格式化状态或输出日志。

## Wi-Fi 配置：AP＋STA 同时运行

03 项目独立编译、独立烧录，不更改 02 的源码、配置和构建目录。两种网络接口同时提供相机与控制服务。

- 热点名称沿用 02：`SmartVehicle-CAM`；密码：`123456789`；WPA2-PSK，最多两台设备接入。
- 热点入口：`http://192.168.4.1/`，视频为 `:81/stream`，运动服务为 `:82`。
- 路由器凭据已从 02 的 `include/wifi_credentials.local.h` 原样复制，继续使用相同 SSID 与密码；该文件保持 Git 忽略，不输出到日志。
- 路由器入口由 DHCP 分配；连接热点后可在网页的网络状态说明中查看路由器地址，或从路由器客户端列表查看。
- 路由器不可用时热点仍开启，STA 每三秒重试。路由器断线会保守撤销运动指令，不会主动关闭热点；恢复后需重新操作控制。断线、重连和信道切换可能造成视频停顿或连接重建，必要时手动重新开始预览。
- 未连接路由器时热点初始信道为 6，连接后由驱动跟随路由器信道；不允许通过性能测试接口手动改信道。
- 两种入口共用同一套相机和运动状态，仍只支持一个视频预览、一个运动控制连接。不提供 NAT/互联网转发或自动弹出配网页面。
- 路由器局域网应避免使用热点的 `192.168.4.0/24` 网段；网段冲突会影响地址路由。

网页同时展示热点就绪状态、STA 连接状态和两个访问地址；视频浮层的无线信号优先显示路由器 RSSI，未连接路由器时显示热点客户端中的最弱 RSSI，并标明来源。

`GET /status` 新增 `network` 对象：`mode="apsta"`、`ap_ready`、`sta_connected`、`ap_ip`、`sta_ip`。未取得 STA 地址时 `sta_ip="0.0.0.0"`；`connected` 表示任意接口就绪，不表示 STA 一定已连接。

## 硬件与配置

相机引脚采用乐鑫 CameraWebServer 的 AI-Thinker 映射：

| 信号 | GPIO |
|---|---|
| PWDN / RESET | 32 / 不使用 |
| XCLK | 0 |
| SCCB SDA / SCL | 26 / 27 |
| D0 / D1 / D2 / D3 | 5 / 18 / 19 / 21 |
| D4 / D5 / D6 / D7 | 36 / 39 / 34 / 35 |
| VSYNC / HREF / PCLK | 25 / 23 / 22 |

默认配置开启 PSRAM（40 MHz）与可选 OLED，UART 控制台关闭；Flash 配置为 4MB，使用单个大应用分区。
系统 socket 额度设为 20；三个 HTTP 服务按内部九项、客户端最多八项保守预算，另为 DHCP 等网络操作预留三项。运动服务禁用 LRU 淘汰，避免只读查询抢掉有效控制长连接。
Wi-Fi 使用 16 个静态 TX 缓冲，TCP 发送缓冲从 5760 增至 23040 字节；接收缓冲、Wi-Fi 协议和发送超时保持原配置。
网页与视频连接在接受时统一启用并回读 `TCP_NODELAY`，减少 HTTP 头部及 MJPEG 小块数据的合并等待。
CPU 默认运行在 240 MHz；相机任务固定在 CPU1，与 CPU0 的 Wi-Fi 任务分开。
系统动态电源管理和 STA 未连接省电均关闭；AP、STA 启动后都显式设置并回读 `WIFI_PS_NONE`。CPU 空闲不表示降频或进入 Wi-Fi 省电。
Wi-Fi 发送功率上限向 SDK 请求 20 dBm，同时打印回读值。当前板启动回读为 60 个 0.25 dBm，即 15 dBm；限制来源尚未确定，不能把 API 设置成功写成实际已有 20 dBm 发射功率。
按 UXGA 和高画质分配 PSRAM 帧缓冲，再将传感器设置为 VGA，支持运行时增大分辨率。当前默认两个缓冲，可通过 `Camera frame buffer count` 改为一个。
采用 `CAMERA_GRAB_WHEN_EMPTY`：后台在空闲缓冲中采集，全部缓冲占用后等待，归还缓冲后继续；没有查看视频时不会无限覆盖队列。这不是停止传感器时钟，也不保证硬件采集帧率等于网页的发送上限。
初始化时清理每个缓冲可能保留的最大分辨率旧帧。视频将 MIME 头、JPEG 和结尾复制到可复用的 PSRAM 缓冲，随后立即归还采集帧；每帧只调用一次 HTTP 分块发送，避免三个 HTTP chunk 的额外小包。
发送缓冲按 4 KiB 扩容，连接关闭时释放，额外占用约一张当前 JPEG 加头部的 PSRAM；扩容失败会明确终止预览并归还原帧，不保留半初始化状态。
GPIO4 的补光灯保持未启用；本工程不使用 TF 卡，GPIO13/14 分配给电机 I2C 总线。
检查相机排线插牢，使用稳定的板载 5V 供电与公共地。

PSRAM 未就绪或传感器不为 OV2640 时会记录错误并停止相机服务初始化。
高分辨率、高画质、弱光或较差的 Wi-Fi 信号会降低实际帧率；发送限速不等同于修改传感器硬件帧率。

## HTTP 接口

| 接口 | 方法 | 功能 |
|---|---|---|
| `http://IP/` | GET | 中文控制网页 |
| `http://IP/status` | GET | 当前参数与发送帧率 JSON |
| `http://IP/control` | POST | 表单 `var=quality&val=12` 等设置 |
| `http://IP/stop` | POST | 结束当前视频代次 |
| `http://IP/capture` | GET | 单张 JPEG |
| `http://IP:82/motor` | GET | 独立电机状态，不等待相机采集或控制任务 |
| `http://IP:82/motor` | POST | 三轴运动指令或全零停车，返回独立电机 JSON |
| `ws://IP:82/motor/ws` | WebSocket | 网页使用的固定 12 字节运动帧及低频紧凑状态 |
| `http://IP:81/stream` | GET | MJPEG 视频 |

控制参数名：`size`（0–5，按上文分辨率顺序）、`quality`、`max_fps`、`brightness`、`contrast`、`saturation`、`hmirror`、`vflip`，以及 `auto_exposure`（0/1）和 `exposure_us`（手动积分时间，整数微秒）。非法参数、超出当前范围或自动曝光时提交手动曝光返回 400。
例如关闭自动曝光：`var=auto_exposure&val=0`；设置约 10 ms：`var=exposure_us&val=10000`，设备按行周期取整后回显。
`/status` 增加 `auto_exposure`、`exposure_valid`、`exposure_us`、`exposure_min_us`、`exposure_max_us` 和 `line_us`；只有 `exposure_valid=true` 时曝光数值才有效。
运行状态位于 `runtime` 对象：`cpu_valid`、`cpu_mhz`、`cpu0_pct`、`cpu1_pct`、`internal_free`、`psram_free`、`wifi_mode`、`rssi_valid`、`rssi_dbm`、`ap_clients`、`video_Bps`、`frames`、`capture_ms`、`send_ms`、`window_ms`。
顶层 `runtime_age_ms` 表示运行快照年龄，`-1` 表示尚未发布；`video_active` 表示视频连接正在处理，不能等同于持续成功发送。
控制页面面向当前局域网内使用，不配置公网映射。

## 四轮电机接线与使用

以根目录 `index.html` 的 PCA9685＋两块 TB6612FNG 方案为准，较早 `接线图.html` 的 L298N 方案不适用于本驱动。

| 接口 | 连接 |
|---|---|
| PCA9685 SDA / SCL | ESP32 GPIO13 / GPIO14，软件 I²C；相机 SCCB 使用独立硬件 I2C1 |
| PCA9685 地址 | 默认 `0x40`，A0–A5 不置高；可在 menuconfig 修改 |
| PCA9685 VCC / GND | 3.3V / 公共地；SDA、SCL 上拉只能接 3.3V，建议确认板载外部上拉 |
| PCA9685 OE | 必须保持低电平使能，不可悬空；不使用 V+ 为电机供电 |
| 第一块 TB6612 A：M1 左前 | CH0→PWMA，CH1→AIN1，CH2→AIN2 |
| 第一块 TB6612 B：M2 右前 | CH3→PWMB，CH4→BIN1，CH5→BIN2 |
| 第二块 TB6612 A：M3 左后 | CH6→PWMA，CH7→AIN1，CH8→AIN2 |
| 第二块 TB6612 B：M4 右后 | CH9→PWMB，CH10→BIN1，CH11→BIN2 |
| 两块 TB6612 VCC / STBY | 均接 3.3V，所有 GND 共地 |
| 两块 TB6612 VM | 独立 6V 电机电源，不能由 ESP32 的 3.3V 供电 |

默认开启电机模块，无自动运动、上电试转或网页打开即运动。初始化先关闭 PCA9685 全部通道，约 1017 Hz PWM；CH12–CH15 保持关闭。
电机初始化失败会保留摄像头功能，网页显示电机故障；排除接线、地址或供电问题后重启，故障期间不接受运动请求。
`menuconfig` → `Vehicle Motor Control` 可禁用电机、更改地址或配置四轮方向反向掩码。

架空车轮、低占空比核对 M1–M4 的正向；bit0/1/2/3 对应左前/右前/左后/右后，某轮反向就设置对应位。
例如右侧两轮需反向时设 `MOTOR_INVERT_MASK=0xa`；实际取值以接线为准，不能直接假定此示例适合当前车辆。
混控假设标准 X 型麦轮布置：`FL=f+r+t`，`FR=f-r-t`，`RL=f-r+t`，`RR=f+r-t`；超出 ±100 时四轮同比例归一化。
轮胎安装方向或轮序不同，需要先纠正安装和映射；普通四轮不能用此麦轮平移控制。
这里的“速度”是开环 PWM 占空比，不包含编码器轮速反馈或闭环调速；网页斜向操作分摊两个轴的输入，使轮占空比不超过滑块上限。

网页自动建立 `ws://当前设备地址:82/motor/ws`，按住按钮后每 100 ms 推送最新目标，不等待逐条回报，也不创建周期 HTTP 请求。连续重复目标只更新板端期限，不重复写 I2C。
正常运动状态每 500 ms 合并回报，运动开始、停车、代次变化和故障立即尝试回报；空闲时每秒在同一连接发送只读查询。状态文本含 `e/r/m/f/g/s/c`，分别表示启用、就绪、运动、驱动故障、停车代次、已处理序号及本次结果。
板端将短 WS 头和状态正文拼成一次 `MSG_DONTWAIT` 写入；缓冲满时不阻塞接收、不累积历史回报，下一条输入再发送最新状态。若写入半帧，则关闭连接并停车，避免后续帧错位。不能仅凭 SDK 函数名里的 async 判断其是否阻塞，此处不使用逐条同步 WS 应答。
浏览器发送缓冲暂未清空时，车轮和机械臂各只保留一个最新待发目标，每 20 ms 重试；停车、机械臂保持／释放优先于普通目标和查询。短暂发送繁忙不会直接关闭连接；只有持续积压达到 200 ms 等传输故障才关闭，并尽力执行现有备用停车流程。
建连允许 4 秒；回报超过 1.5 秒显示“状态回报延迟”，超过 2.5 秒则停止本地推送、关闭连接并尝试备用停车。反馈期限与板端 500 ms 无有效输入停车独立，替代旧版逐条 300 ms 超时。重连不恢复旧按住，必须重新操作。
网页从同一设备地址生成 82 端口连接，无需手动输入运动地址；路由器或访问环境需要允许 80、81、82 三个端口。WS 握手前要求 Origin 为本设备 80 端口网页，额外控制页面不能抢占已连接页面；HTTP 诊断仍允许无 Origin 的本地命令行 GET。
相机 `/status` 读取缓存，图像设置生效、视频开始/结束及约每秒帧率统计时更新缓存，不再等待可能持续四秒的取帧。网络、电机字段在请求时取快照。即使抓拍或相机设置阻塞 80 端口，运动接收仍由 82 端口独立执行；相机轮询失败不会单独中断健康的运动通道。
每次按下先在长连接发送停车，收到对应序号之后的状态确认、新的 `generation` 后才发送非零目标；确认前松手会取消该次操作。松手停车递增服务端代次，旧目标不能重新启动电机。连接关闭时，板端立即投递停车给独立监视任务。
独立停车任务不等待相机或 HTTP 服务空闲；正常调度下超时停车延迟约为 500 ms 加最多一个 50 ms 检查周期及 I2C 操作耗时，不是硬实时保证。
指令接收也检查 500 ms 期限，监视任务尚未调度时，迟到包同样不能延长旧指令。超时前打印 `Command timeout age_ms=...`；有效续期间隔达到 250 ms 时打印 `Command renew late gap_ms=...`，用于区分请求延迟与 I2C 故障。
反向前先关闭所有输出，再留足 tick 边界余量等待至少 2 ms，之后改变方向；相同指令只更新期限，不重复写 I2C。
目前只面向一个车辆控制页面，额外页面的 WS 握手会被拒绝；应关闭旧控制页面再换设备或标签页操作。只读 HTTP GET 的连接关闭不会触发停车。

HTTP 诊断/备用接口表单示例：`forward=30&right=0&turn=0&generation=2`，三个轴均为 -100..100，向前、向右平移、顺时针分别为正。存在 WS 控制连接时只允许 HTTP 全零停车，非零 HTTP 目标返回 409，避免两个控制通道混用。
全零 `forward=0&right=0&turn=0` 无需代次，返回 `generation` 供下一次运动使用。
成功返回电机 JSON；非法参数返回 400 并停车，旧代次或电机未就绪返回 409，外设操作失败返回 500。
`/status` 新增嵌套 `motor`，其中 `wheels` 为反向修正前的四轮占空比，`moving` 仅表示存在有效运动指令，不能作为实际轮速或物理停车反馈。
原 80 端口 `/stop` 仍只停止视频；车辆停车使用 82 端口 `/motor` 的全零指令。升级后需刷新网页，旧页面使用的 80 端口 `/motor` 不再注册。

车轮 WS 命令固定 12 字节：byte0 为操作（0 查询、1 运动、2 停车，机械臂使用 3～8，见下文）；byte1–3 为 `forward/right/turn + 100`，范围 0–200；byte4–7 为停车代次、byte8–11 为非零递增序号，两个整数均为大端。重复/倒序序号、非法长度或类型会关闭控制连接。查询不写电机外设，停车不要求旧代次匹配。正常心跳是每秒 120 字节应用数据，另加 WS/TCP/IP/Wi-Fi 协议开销；这不是实测空口总流量。

本次并发修复保留 500 ms 自动停车期限和相机时钟、双缓冲、帧率参数；模拟与编译检查不能代替视频加实体电机的上板联动验证，无线链路持续延迟超过期限时仍应停车。

2026-10-21 修复前只读实测：`192.168.1.11` 的 82 端口和 Origin 均正常；开视频时 40 次电机 GET 均为 HTTP 200，但 14 次超过 300 ms，3 次超过 1 秒，最长约 1.16 秒，旧超时策略会误报端口不可达。同一视频连接按每段 8 秒进行“仅视频/并发电机只读查询/停止查询”短时对比，完整帧分别为 10/2/8，即 1.25/0.25/1.00 FPS，已复现纯通信并发影响。没有发送运动或停车命令，开始和结束时电机均未运动、无故障、代次均为 23；此短测不代表长期帧率，也未隔离真实电机转动带来的供电或干扰影响。

以下为复制自 02 的历史验证记录，不代表 03 的 AP＋STA 实机验证：STA 和独立 AP 完整构建均通过，未发现编译警告，应用分区约剩余 32%。前端模拟在回报延迟 1.2 秒时仍每 100 ms 推送目标，并验证停车确认前松手、断线、积压、重连、退出和页面缓存恢复不会恢复旧运动。本机桩直接执行生产协议及视频函数，覆盖来源和单控制连接校验、12 字节解码、2 Hz 回报、EAGAIN 合并、半帧发送失败、关闭停车、旧指令拒绝、重复目标不重复写 I2C、JPEG 合并，以及首次分配/后续扩容/发送失败后的资源归还。本轮不自动烧录或驱动实体电机，新的实机帧率和联动效果需烧录后验证。

## 预览失败时的检查信息

视频开始时串口记录请求进入、首帧字节数、尺寸、JPEG 起始标志、取帧耗时和首帧发送耗时。
启动时应出现 `Wi-Fi TX config type=0 static_buffers=16 tcp_snd_buf=23040`；新 HTTP 连接应出现 `tcp_nodelay=1`。
发送失败会记录合并帧阶段 `frame_packet`、原始 `errno`、已完成帧数、发送耗时，以及可取得的 Wi-Fi 信号强度和内部可用内存；发送缓冲扩容失败会记录 `TX_BUFFER_NO_MEMORY`。
03 在 STA 在线时显示路由器信号，否则显示热点客户端信号；发送失败时记录热点状态和接入数量。
`errno=11` 表示发送等待超时，`errno=104` 表示对端重置连接；两者都不能单独证明 Wi-Fi 断线。
网页分别提示响应超时、HTTP 服务错误、返回数据错误或网络请求失败；状态请求不会重叠堆积。
相机 HTTP 请求使用 XMLHttpRequest 五秒超时，运动改用 WS 独立推送；仅在异常时使用一次 1.5 秒 HTTP 备用停车。协议逐帧收发细节使用 DEBUG 日志，连接变化、硬件写入、停车和错误仍保留业务日志。
本次修改后需要重新烧录固件并刷新网页，开发板才会使用新的服务配置和嵌入页面。
是否达到 10 FPS 以完整 JPEG 的实际接收数量为准，编译成功或设置上限为 10 不代表实测通过。

## 可选机械臂控制（免焊接、两块 PCA9685）

车轮板 SDA 固定 GPIO13，机械臂板 SDA 固定 GPIO2，两板 SCL 共接 GPIO14；GPIO12 始终不接，OLED 原接线不变。两板地址保持 0x40，SDA 不可相连。固件现在由共享的 `Pca9685Bus` 实例和总线锁统一串行执行软件 I²C，支持 ACK、单寄存器回读、九拍恢复与 20 ms 事务超时，不与相机的硬件 I²C 或 LEDC 争用。接口级日志保留为 INFO，逐 GPIO 边沿与微秒延时调用采用 DEBUG，默认 INFO 构建不输出这些高频调试日志。

`Optional Robot Arm` → `ARM_ENABLED` 默认开启；缺失机械臂板只禁用机械臂，不阻止车轮与相机启动。关闭后不配置 GPIO2，车轮仍固定 GPIO13/14。关节 0/1 对应新板 CH14/CH15，分别配置约 50 Hz；车轮板约 1017 Hz。上电先撤销历史输出，机械臂不回中、不自动试转，收到设角度指令后才输出脉冲。

网页增加两个关节的目标角度输入、软件限位提示及明确的“释放两个关节”按钮。默认标称角度范围为 5～175 度，分别由 `ARM_JOINT0_MIN/MAX`、`ARM_JOINT1_MIN/MAX` 调整；脉宽按 0～180 度映射至 1000～2000 μs。默认范围不能保证适合任何机械臂，首次卸载连杆并从中位校准，不把软件角度视为实际反馈。超范围请求直接拒绝、不裁剪、不写硬件。

接口位于原运动端口 82，沿用车轮的同设备网页来源校验，不访问相机锁：

- `GET /arm`：返回 `enabled`、`ready`、`fault`、`generation`、`angles`、`holding`、`minimum`、`maximum`。数组顺序为 CH14/CH15；`angles` 为最后成功下发的角度，`targets` 为当前平滑目标，`slewing` 表示仍在推进；-1 表示尚未设置。`holding` 只表示已确认启用输出，不代表舵机到位。
- `POST /arm`，表单 `action=set&joint=0&angle=90&generation=N`：N 必须取最近一次状态中的 generation。每次有效设角度尝试递增代次，迟到或重复旧命令返回 409；非法参数或越界返回 400，设备不可用/驱动失败返回 503。
- `POST /arm`，表单 `action=release`：关闭两路 PWM，不回中、不移动车轮，并作废旧角度指令。释放不要求代次；承重机械臂可能下垂。

网页命令不自动重试，不在恢复网络后重放动作。网络断开或车轮控制连接关闭时，使机械臂旧命令代次失效，但保留当前舵机保持力矩；车轮仍按原 500 ms 期限停车。机械臂写失败后尽力关闭该板输出，标记故障；未收到关闭确认时实际状态未知。PCA9685 会保持硬件输出，I²C 断线或 MCU 失效时软件无法保证释放或停车。

SG90 从现有 XL4015 #2 的稳压 5V 输出单独分支供电，VCC 仍接 3.3V，OE 接公共地；舵机电流不经过面包板或 ESP32，需带载检查总电流与压降。烧录前断开 GPIO2→机械臂 SDA，并按 OLED 要求断开 U0T/U0R；烧录结束移除烧写板后恢复。无需焊接地址焊盘，不需要第三块 XL4015。

本次实现未自动烧录或操作实物；软件 I²C 时序、两个 SG90 的实际限位、5V 带载稳定性及视频/车轮联动仍需在真实硬件确认。


## 模块边界与审查入口

- `include/pca9685_bus.h`、`source/pca9685_bus.cpp`：共享软件 I²C，唯一管理开漏 GPIO、分支选择、ACK、事务超时和恢复；不知道车轮或关节业务状态。
- `include/motor_control.h`、`source/motor_control.cpp`：只管理四轮混控、方向切换、代次和 500 ms 超时停车；状态不再包含机械臂字段。
- `include/arm_control.h`、`source/arm_control.cpp`：独立管理机械臂初始化、限位、脉宽、目标、释放及原子命令代次；通过同一 `Pca9685Bus` 实例访问另一数据分支。
- `include/oled_display.h`、`source/oled_display.cpp`：独立管理 SPI2、SSD1306 初始化、字符绘制及显存发送；只接收 `OledState`，不采集 CPU、曝光或网络数据。
- `CameraWeb`：拥有共享总线与控制模块，负责 HTTP 参数与响应、启动顺序、网络事件协调、CPU / 曝光采样和显示快照准备。曝光十秒失效判断仍在数据来源层完成，SPI 发送在释放快照锁后进行。

总线实例先于两个控制模块创建、晚于它们销毁。两个模块先取各自状态锁，再调用内部取锁的总线事务；总线不会回调业务模块，因此不会反向获取状态锁。每次完整 I²C 事务独占共享 SCL，不复制总线锁、不创建第二个 GPIO14 驱动。车轮监视任务在共享总线销毁前退出。

网络事件由应用层分别投递车轮停车、原子递增机械臂命令代次；不会在 Wi-Fi 回调中等待总线或释放承重扭矩。`/motor`、`/motor/ws`、`/arm` 的协议字段、网页交互、固定引脚、默认限位和可选模块配置保持不变。


## 键盘驾驶与机械臂连续增减

电脑网页中，按住 W/S 前进/后退，A/D 左右平移，Q/E 原地左转/右转，Z/X 左前/右前，C/V 左后/右后；空格停车。松开当前按键、窗口失焦或切后台停车，不自动恢复旧方向；输入框、下拉框和可编辑区域不触发键盘驾驶。多个方向键不叠加，当前动作松开后需重新按键。仍使用车轮 500 ms 指令超时停车。

机械臂保留固定角度设置，关节 0/1 对应 CH14/CH15。新增 `POST /arm` 表单：

- `action=increase&joint=0&step=15&generation=<当前代次>`：平滑目标增加 15 度。
- `action=decrease&joint=1&step=15&generation=<当前代次>`：平滑目标减少 15 度。

`step` 只接受 1～15 的整数，关节只接受 0/1。首次需用 `action=set` 设置初始目标；未设置目标的关节拒绝增减。增减续租不改变 `generation`；新固定目标、保持、释放、网络作废或超时会更新代次，后续请求使用最新状态，禁止重放旧请求。增量计算和限位处理在机械臂业务锁内执行，超出边界时停留在配置的软件限位。限位提示仅基于目标值，不代表检测到物理限位。

网页通过现有 WebSocket 每 100 ms 更新一次目标，每条指令增减 15 度，不等待上条回报；ESP32 在本地约每 20 ms 最多推进 2 度。松开、失焦或隐藏页面会发送保持指令，丢弃未完成目标；断流超过 350 ms 则由本地任务停止推进，保持最后输出。机械臂键盘：J/K 控制关节 1 减小/增加，U/I 控制关节 2 减小/增加，按住连续调节、松开保持。


## 网络切换后的运动连接回收

03 的 82 端口中，`/motor` 和 `/arm` 的普通 HTTP 响应发送完成后会关闭会话，不占用后续 WebSocket 的接入位置。控制 WebSocket 仍只允许一个页面占用，正常操作者不会被其他页面抢占。

网页空闲时每秒查询一次运动状态，行驶时每 100 ms 下发目标。固件每 500 ms 在运动服务任务中巡检：控制连接三秒未收到有效帧后，先投递停车，再关闭旧会话；在实际关闭回调中清除占用状态。连接回收和业务处理在同一 HTTP 任务串行执行，队列繁忙时只保留一次巡检请求。TCP 保活作为半开连接回收的补充。

切换热点／路由器入口后，网页沿用原有自动重连机制，旧连接回收与重试可能需要数秒。旧页面仍在线且持续发送有效查询时，新页面会被拒绝，需要先关闭旧控制页面。车轮原有 500 ms 指令超时停车保持不变；三秒连接回收期限不会延长车轮运动期限。

本次 ESP-IDF 构建及生产回调的本机桩验证通过，覆盖正常心跳不误回收、过期连接释放、短 HTTP 回收、有效操作者不被抢占、迟到帧拒绝、关闭或工作队列失败后重试。尚未烧录，网络切换效果仍需开发板实测。


## 平滑机械臂与板载补光灯（02／03 通用）

机械臂仍由 `arm_control.h/.cpp` 管理，车轮和机械臂共用 `/motor/ws` 持续连接，但各自使用独立的状态代次。网页不再为每次舵机动作建立 HTTP 连接。现有 `/arm` HTTP 接口保留作诊断及单次命令调用，返回值中增加 `targets` 和 `slewing`。

- 首次设置角度前，PWM 保持关闭。没有位置反馈时无法知道初始实际角度，因此第一次明确设置（或释放后重新设置）直接建立初始输出；之后的目标由本地任务平滑推进。
- 固定目标提交后约每 20 ms 最多推进 2°。连续增减每条指令将最新目标增加／减少 15°，只保留一个最新目标，不排队历史动作。
- 连续控制每 100 ms 续租，不要求每步等待响应；350 ms 无有效增减指令会停止推进并更新代次。松手、失焦、切后台发送保持指令，丢弃未完成目标，保持最后输出。固定角度指令无需连续续租，但网络作废或保持指令同样可以停止它。
- 达到软件限位时停止继续推进；上位机根据最后下发角度触发限位提示。I²C 写入失败后停止任务输出更新并报告故障，不自动重试移动。两个关节仍接机械臂板 CH14、CH15。
- `angles` 为最后成功下发的标称角度，`targets` 为目标，`slewing` 为软件推进状态，均不是 SG90 的实际位置反馈。机械负载和供电造成的卡顿需要实机确认。

共享 WS 的机械臂帧仍为 12 字节：byte0 为动作；byte1 为关节 0／1；byte2 为步长或固定角度；byte3 必须为 0；byte4～7 为机械臂代次，byte8～11 为整条连接共用的递增序号，均为大端。车轮动作 0～2 的字节布局保持原样。

| 动作 | byte0 | byte1 | byte2 |
|---|---:|---:|---:|
| 目标增加 | 3 | 关节 | 1～15，网页固定 15 |
| 目标减少 | 4 | 关节 | 1～15，网页固定 15 |
| 停止推进并保持 | 5 | 0 | 0 |
| 设置固定角度 | 6 | 关节 | 软件范围内的 0～180 |
| 释放两路 PWM | 7 | 0 | 0 |
| 查询机械臂状态 | 8 | 0 | 0 |

机械臂回报为 `type="arm"`，包含已处理序号 `s`、结果 `c` 以及 `/arm` 的完整状态字段。车轮紧凑回报格式保持不变，二者分别处理，机械臂拒绝命令不会直接切断车轮连接。

“查看单张照片”右侧新增“打开补光灯／关闭补光灯”按钮，使用 AI-Thinker ESP32-CAM 的 GPIO4 白色补光灯，普通高低电平输出，不占用相机的 LEDC 时钟。依据：[Espressif 板型引脚定义](https://github.com/espressif/arduino-esp32/blob/master/libraries/ESP32/examples/Camera/CameraWebServer/camera_pins.h)。当前固件不启用 microSD。

上电默认关闭；`POST /led` 表单只接受 `enabled=0` 或 `enabled=1`，返回 `led_ready`、`led_on`、`led_fault`。`/status` 同步携带这些字段，网页只在确认结果后更新按钮，失败后通过后续状态查询恢复显示，不自动翻转重试。该状态为成功写入的逻辑值，不是发光反馈。

本次验证：两个工程均完成 ESP-IDF 构建；本机桩直接执行生产平滑模块与协议回调，检查角度推进、限位、350 ms 断流停止、保持／释放、旧代次拒绝、共享连接分派、WS 扩展长度、发送拥塞及 GPIO 开关错误处理；两个网页的生产脚本验证通过。未自动烧录，实际运动流畅度与补光灯效果需烧录后确认。


## 共享控制连接的短暂繁忙处理

02 与 03 同步修复：短暂的 WebSocket `bufferedAmount > 0` 不再等同于发送失败。待发区按车轮目标、机械臂目标、车轮停车、机械臂单次动作及两类查询分别合并，每类至多保留一个待发项。停止请求会丢弃对应未发送的运动目标，并优先发送；固定角度和释放等单次命令可以有界等待发送空间，不因瞬时繁忙立即报断连。

发送序号只在实际发送时递增；排队中的停车或机械臂单次操作尚未绑定发送序号时，旧回报不能提前完成确认。松手、失焦、页面离开、失效代次及重连后均不恢复旧手势或历史待发目标。真实持续拥塞达到 200 ms 时仍停止续期并关闭连接，车轮 500 ms、机械臂连续推进 350 ms 的设备端超时期限保持原样。

对于格式有效、但因旧代次或驱动状态被拒绝的车轮命令，服务端返回业务结果，浏览器停止当前车轮手势并显示原因；共享连接和机械臂通道继续可用。需要重新按下才能再次运动，不能通过刷新代次自动恢复。畸形协议、回报传输失败及原有连接超时仍按连接故障处理。

验证已分别执行两个项目的生产网页脚本，覆盖原始 12 字节瞬时积压、最新目标合并、停止优先、延迟序号确认、车轮／机械臂同时操作、固定目标等待、旧代次停止、持续拥塞和页面离开；生产协议回调验证业务拒绝后仍可查询、发送失败仍返回失败。两个工程均编译通过；未自动烧录，仍需实机确认无线网络和供电条件下的表现。

局部标签切换验证：两个项目均通过 HTML 层级、控件 ID 和交互回归检查；本机浏览器测量确认 Tab1／Tab2 的预览、预览按钮、运行参数区域坐标一致，FPS 上限显示位于设置输入框右侧。隐藏页不接收焦点或输入。固件已分别编译，尚未自动烧录及实机验证。


操作区细节：Tab1／Tab2 按钮放在补光灯按钮右边，窄屏自然换行；车辆与机械臂的使用说明、快捷键和软件范围放在控制按钮下方。车辆速度滑块初始值为 45% PWM，占空比设置不会自动启动车轮。

手机控制：按钮禁止文字选择与 iOS 长按呼出菜单，并拦截按钮上的 selectstart／contextmenu；方向与关节增减按钮继续使用 touch-action: none 和原有指针捕获、松手停止逻辑。角度等输入框及普通说明文字仍可编辑、选择和复制。

视频浮层逐项变色：实际发送 FPS 小于 5 时变红；CPU0、CPU1 各自超过 90% 时变红（5 FPS 和 90% 仍为绿色）。车辆、机械臂连接断开或状态未知时变红，包括等待首次状态与连接重建、状态回报延迟和停车未确认；收到有效状态后恢复绿色。积分时间、Wi-Fi 与其余项目保持绿色；数值采样失效显示 --，清除该数值的旧告警色。相机状态请求失败不会覆盖独立运动连接的状态颜色。
